# Owned Dodo target HTTP contract v1

Runnable root `dodo-target/`. Healthy base `http://127.0.0.1:3300`; disclosed broken control `3301`; an actual changed-source repair preview retains the original `broken` mode and may use `3302` or a separately registered loopback port3310–3399. These are distinct from backend fixture/provider ports. Primary supplied privately approved distinct Test Mode keys and one-time USD 100-minor-unit tax-inclusive product `pdt_0NpSJqlzKkRpa8IfLD3gU`. No payment or webhook secret supplied yet. Genuine payment and provider-signed delivery remain unverified.

App registration pins `GET /api/target/manifest` before fixture creation. Controller calls use server-side `Authorization: Bearer <TARGET_CONTROL_TOKEN>`. Never put controller/provider credentials into browsers or model prompts. Cookie mutations require `Origin` equal to the configured app origin. All JSON control bodies reject unknown fields. Errors use `{error:<code>}` and an appropriate 4xx/5xx status.

| Method/path | Request and result |
| --- | --- |
| `GET /api/target/manifest` | Public manifest with `contract_version`, `target_id`, `target_revision`, `source_sha256`, `source_commit`, `source_clean`, upstream SHA, adapter, mode/fault, `repair:{source_file,disposition}`, exact safe origins, checkout origins and one-time product. Source commit/clean are from the production build; dev/source-only runs have null values. |
| `GET /api/target/readiness` | Public `{ready,errors:[{code,action}],warnings:[{code,action}],webhook_ready,manifest,evidence_source,provider_baseline_verified:false}`. Configuration readiness only. Missing keys/product/amount/currency/controller, unsafe origin, unconfirmed key scope or stale build keep ready false. Missing webhook secret is a warning and `webhook_ready:false`, not a checkout/reconciliation blocker. This does not assert delivery reachability. DB startup failure is explicit `503 database_unavailable`. |
| `POST /api/target/fixtures` | Controller body `{run_id,persona_id,target_revision}`; `201 {run_id,persona_id,account_id,fixture_id,target_revision,login_token,login_url}`. NEW random isolated account every call. No caller-selected email/account. A closed run cannot reopen. |
| `POST /api/target/login` | Body `{login_token}` plus exact `Origin`. Single-use token expires in five minutes, logs into only its assigned active fixture and returns ownership plus HttpOnly/SameSite=Strict one-hour session cookie. No OAuth or inbox required. `login_url` is `/target/login#token=...`; the browser removes the fragment before login. |
| `POST /api/target/reset` | Controller body `{run_id,target_revision}`; revokes only that run/revision’s local accounts and orders, invalidates its sessions/login tokens through account revocation, preserves provider evidence and event ledger. No provider mutation or global reset. |
| `GET /api/target/products` | Public one-time Special Downloads product, quantity one, twelve local demo sample files, configured amount in minor units, currency and checkout readiness. |
| `GET /api/target/me` | Session cookie; own ownership, local orders and actual account access. No grants or provider reads. |
| `POST /api/target/checkouts` | Session cookie + exact `Origin`; body `{}`. Server creates a new owned order, synthetic Dodo test customer and checkout for every deliberate attempt. `201 {order_id,checkout_session_id,checkout_url,ownership,source}`. Source is `dodo_test_api` in the runtime. Missing setup returns `503 setup_required`; provider failure `502 provider_checkout_failed`; unapproved checkout origin `502 provider_checkout_origin_forbidden`. Card entry only (credit/debit), saved methods hidden, generated email/name editing disabled, short links false. No automatic payment mutation retries. |
| `GET /api/target/orders?account_id=...` | Controller; owned order list with checkout ID, state, product, expected amount/currency and run/persona/account/fixture/revision IDs. Obtain these after the browser journey. |
| `GET /api/target/receipts?order_id=...` | Controller; independent read-only provider lookup `GET /checkouts/{id}` then `GET /payments/{payment_id}` with the DISTINCT read-only key. `{state,source,ownership,checkout_session_id,evidence_id,...}`. State is `succeeded`, `pending`, `failed`, `mismatch`, `provider_error` or `setup_required`. Success needs succeeded on both resources, matching all server metadata IDs, customer ID/email, product/quantity, checkout/payment linkage, amount and currency. Does not grant or alter app paid state; appends immutable sanitized observation evidence only. |
| `GET /api/target/entitlements?account_id=...&order_id=...` | Controller; separate read-only LOCAL app oracle `{source:'app_local_entitlement',has_access,order_has_grant,grant_count,account_grant_count,active,ownership,payment_id}`. `has_access` is actual account capability, including a prior paid order; `order_has_grant`/`grant_count` isolate this specific purchase. Wrong account/order is `409 account_order_mismatch`. Reads cannot grant or write. |
| `GET /api/target/evidence?evidence_id=...` | Controller; immutable sanitized observation/webhook evidence, with ownership and source labels. No secret, card, billing or raw customer email fields. Signed raw body has SHA256 plus sanitized fields, not sensitive raw bytes. Evidence and event ledger are protected against update/delete. |
| `POST /api/webhooks/payment` | Raw-body official SDK unwrap with webhook-id/signature/timestamp. Current `payment.succeeded` envelope, server-owned order binding plus independent provider verification before atomic event-ledger/shared-fulfillment-ledger/grant commit. Duplicate delivery applies once. Bad signature `401`; wrong identity/product/price `409`; unknown order `404`; unsettled payment `409`; provider read error `502`. Other authenticated event types are ignored. Missing webhook secret returns `503 webhook_not_configured`; reconciliation does not bypass this route. `grant_applied:false` on a later valid event when recovery already granted. |
| `POST /api/target/reconcile` | Active session cookie + exact `Origin`, strict body `{order_id}` obtained from that session's own app order list. No controller-only access or query authority. Fresh independent two-GET receipt verification with exact ownership/product/customer/amount/currency precedes atomic current revision/account/run/order checks and a shared immutable fulfillment ledger. Returns `{state:'granted'|'already_granted'|'suppressed',source,fulfillment_source,fulfillment_path:'app_reconciliation',grant_applied,evidence_id,receipt_evidence_id,ownership,payment_id,has_access}`. Runtime operation source is `dodo_test_api_reconciliation`, distinct from signed webhook evidence. Duplicate/restarted/cross-path delivery applies once and retains the first fulfillment evidence. Pending/failed/mismatch is `409 payment_not_settled` with explicit receipt state, provider error `502`, setup required `503`; wrong account `409`, no session `401`, wrong Origin `403`, unknown input fields `400`, reset during reads `409 inactive_order`. No payment ID, account, metadata, price or provider response accepted from the browser. |
| `GET /api/target/return` | Session cookie; read-only app access view. Query parameters have no authority and cannot grant. Browser `/checkout/return` calls this endpoint. |
| `GET /api/target/download?artwork=0` | Session cookie; protected file download, indices 0–11. `403 purchase_required` without actual active account entitlement. Capability exercise is separate from oracle reads. |

Fixture auth requires `TARGET_SANDBOX=true`, `TARGET_ENV=local`, private controller token of at least 32 characters and an exact HTTP loopback origin. `TARGET_ENV=production`, remote origins and missing opt-in forbid fixture access. A production-optimized local Next build is allowed only with that explicit loopback sandbox configuration. Server binds loopback. No deployed production auth shim.

Server-only configuration after primary's credential approval: Test Mode write key with Customers Write + Checkout Sessions Write, DISTINCT Test Mode verifier key with Checkout Sessions Read + Payments Read and no Write grants; all other resources None on both. The current dashboard uses granular grants, not the legacy Enable write access checkbox. Optionally supply a genuine test endpoint signing secret after its separate authorization; otherwise signed webhook handling remains disabled with 503. Supply one-time Test Mode product ID, exact tax-inclusive expected amount/currency, scope confirmation flags, control token and per-preview persistent database path. See `.env.example`, README and [INTEGRATION-CHECKLIST.md](INTEGRATION-CHECKLIST.md). Readiness cannot infer opaque key privilege or prove product existence/delivery. No client-public API/webhook key.

Server API origin is strictly `https://test.dodopayments.com`. Firstmate steering 005 explicitly authorizes the separate hosted sandbox origin `https://test.checkout.dodopayments.com`, documented in the [official guide](https://docs.dodopayments.com/developer-resources/checkout-session#api-response). This is the sole browser checkout origin in the manifest. API-host short links, alternate ports, embedded credentials, lookalikes, live hosts and HTTP checkout links are rejected with `provider_checkout_origin_forbidden`. Provider redirects and endpoint overrides are forbidden. Safe app origins are exactly the configured loopback origin per preview. No live host, bank/KYC, real cards, subscriptions, paid trials, deployment or tunnel setup.

Stagehand journey: create fixture outside the browser; open its isolated `login_url`; click “Continue as test customer”; visit `/special-downloads`; click “Get Art Pack”; exercise genuine configured test checkout; return; click “Confirm purchase” to execute the session-owned reconciliation command if access is absent; inspect/download the pack. Backend obtains orders then independently reads receipt and entitlement, checks returned ownership against the journey, and exercises access separately. Pending/unavailable provider state is inconclusive, never zero access inferred from URL/email. Tryfolk backend owns paired-N budgets and orchestration.

The fulfillment-only source seam, export allowlist/protected digests and immutable local red/green commands are [REPAIR-CONTRACT.md](REPAIR-CONTRACT.md). `npm run --silent repair:contract` exports the machine contract; `-- --verify <original-contract.json>` rejects protected-file changes. Only `lib/fulfillment-policy.ts` may change. Keep the original broken mode/product/price on a repair; the manifest fault and effective disposition follow the actual policy source. `npm run test:repair` is intentionally red on the shipped controlled fault and must be green after the source change.

Mode is frozen at process startup. On the shipped source, `broken` discloses `payment-settled-fulfillment-suppressed`: valid independent settlement is recorded but app grant is withheld. `healthy` grants once. `repaired` is no longer a supported mode; a repair must change source and use its exact new revision. The revision hash includes runnable source, mode, product, amount/currency; stale post-build source gates payment. Separate processes/databases and new run accounts/checkouts are required for before/after. Same-persona lineage is owned by backend. A mode comparison does not claim a Codex repair or genuine Dodo evidence.

Local external-provider fixture tests are explicitly labelled `external_provider_fixture`. There is no HTTP switch or runtime fixture provider. Real read observations use `dodo_test_api`; app recovery grants use `dodo_test_api_reconciliation`; authenticated provider event evidence uses `dodo_signed_webhook`. Recovery evidence sets `authenticated_raw_body:false`. It does not claim a signed delivery. Both grant paths share immutable fulfillment/payment binding; receipt and entitlement GETs never call either grant path. Local signature/SDK transport fixtures cannot establish a genuine checkout baseline. Primary-approved provider endpoint/delivery remains required and was not performed. The official CLI has an outbound Test Mode listener to loopback, but its relay/key disclosure, provider endpoint creation/scopes and JSON reserialization require separate authorization, which has not been given. No listener, tunnel or endpoint was started. Unsigned CLI trigger payloads cannot grant. See the integration checklist for the exact future forwarding command and limits.
